01무엇을 만들었나

입고 AMR이 박스를 싣고 오면 입고 로봇(P3020 IN)이 RGB-D 카메라로 박스를 찾아 컨베이어에 올리고, 컨베이어가 지역별로 분류한 뒤 불량 박스는 출고 로봇(P3020 OUT)이 Reject Bin에 적재합니다. 전부 Isaac Sim 안의 디지털 트윈으로 돌아갑니다.

실행 환경은 세 곳으로 나뉩니다. Isaac Sim(내장 Python 3.11 — 물리 · 로봇 에이전트), 호스트 ROS 2(Python 3.12 — Nav2 · 액션 서버 · ONNX 비전 · MQTT), 관제 화면(React · FastAPI · PostgreSQL)입니다. 이 분리가 아래 03의 문제로 이어졌습니다.

02담당 역할

  • P3020 IN Pick & Place — 8단계 상태 기계(접근 → 하강 → 파지 → 들기 → 이동 → 내리기 → 놓기 → 완료)와 Lula IK로 박스를 집어 컨베이어에 올립니다. 박스 위치에 맞춰 그리퍼 방향(yaw)을 정하고, 로봇 베이스 좌표는 USD에서 읽어 맵이 바뀌어도 자동으로 맞춥니다.
  • 비전 결과 연동 — 팀원(서진우)이 학습 · 배포한 YOLO ONNX 검출 픽셀(/box_pixel)에 Depth를 결합해 world 3D 좌표를 계산하고, 중간 높이(0.35 m)에서 다시 검출해 보정합니다. 오검출은 깊이 0.4 m 미만(팔 · 그리퍼 자신) → 박스 색 아님(그림자) → world Z 0.30 m 미만(노란 AMR 몸체) 세 단계로 걸렀습니다.
  • 반복 처리 · 종료 신호 — 박스 수를 미리 정하지 않고 화물이 빌 때까지 반복하며, 박스 단위 진행은 피드백으로, 작업 종료는 5초 미검출 신호(CARGO_EMPTY) 하나로 나눠 AMR 복귀를 요청합니다.
  • 액션 서버 · P3020 OUT — pick_place 액션 서버를 호스트 프로세스로 분리했고(03), IN 에이전트의 흐름 · IK · 비전 로직을 재사용해 Reject Line의 박스를 Reject Bin에 적재하는 출고 에이전트를 만들고 적재 계획 모듈(OutboundLoadPlanner)을 처음 연결했습니다. 최종 통합에서 남은 문제는 제출 뒤 팀장이 보완했습니다.

담당 코드 isaac_sim/robots/p3020/p3020_mission_agent.py · isaac_sim/robots/p3020/p3020_out_mission_agent.py · ros2_ws (pick_place 액션 서버)

03막혔던 문제와 해결 — 두 Python 사이에서 깨지던 액션

상황

Isaac Sim 안에서 커스텀 액션(/p3020/pick_place)을 직접 처리하려 하자 메시지 타입 오류가 났습니다.

원인

Isaac Sim 내장 Python(3.11)과 시스템 ROS 2 Jazzy(Python 3.12)의 런타임이 달라, 사용자 정의 인터페이스를 두 쪽이 공유할 수 없었습니다.

해결

Docker · 내장 라이브러리 재빌드는 2주 일정에 위험이 커 보류하고, 액션 서버를 호스트 Python 3.12 프로세스로 분리한 뒤 Isaac Sim 에이전트와는 표준 타입 토픽 2개로만 명령 · 피드백을 주고받게 했습니다.

결과

두 환경을 고치지 않고도 액션 Goal 수락 · 피드백과 CARGO_EMPTY 복귀까지 전체 미션이 끊기지 않고 이어졌습니다.

04남은 과제

2주 동안 전 공정 연결에 집중해 반복 시험 기반의 정량 성공률은 측정하지 못했습니다. VGP20 흡착을 흡착 컵과 박스 사이 거리 조건으로 모사한 시뮬레이션 검증 단계이며, 센서 노이즈와 지연을 반영한 실기 검증은 다음 과제로 남겼습니다.

05배운 점

  • 맵을 고칠 때마다 깨지던 고정 좌표를 USD에서 읽게 바꾸고 중간 높이에서 Depth 좌표를 다시 보정하면서, 센서 · 로봇 좌표 기준은 통합 전에 먼저 맞춰야 한다는 것을 배웠습니다.
  • 환경을 억지로 맞추기보다 경계를 단순한 표준 타입으로 두는 쪽이 빠르고 안정적일 때가 있습니다.
